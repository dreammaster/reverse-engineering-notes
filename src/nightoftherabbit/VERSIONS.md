## Lua 5.4

`strings` finds `Lua 5.4` and the executable defines `lua_arith`, `lua_compare`, `lua_rotate`, `lua_callk`, `lua_pcallk`, `lua_isinteger`, `lua_tointegerx` and `luaopen_utf8`: **the scripts of this game run in the standard Lua 5.4**, not in Lua 5.1 / LuaJIT as in Deponia 1, 2 and 4 (E).
The data uses it: running the reconstruction (ScummVM's Lua 5.1) on this game's scripts gives `')' expected near '&'` (Lua 5.3's bitwise operators, e.g. in the scripts `(30,307)`, `(30,308)`, `(30,328)`, `(30,382)`, `(30,409)`), and the scripts that fail to compile leave functions undefined later
(`attempt to call global 'IsNotEmpty'`, `attempt to index global 'ButtonManager'`) (R, D). So **a ScummVM engine for this game needs Lua 5.3/5.4 syntax and integers** (ScummVM's `common/lua` is 5.1); this is the main thing that separates it from the Deponia builds.

## What the listings say about the changes above (4 Nov 2026)

Read in `rabbit.asm` and `Deponia_Linux.asm`; each item says how far it was read.

- **`TFile` is the same code with its members moved (read: `ReadByte`, `ReadLong`, `ReadMem`).** The flow is the same in both: the position against the length (`-1` is no limit), `wxFile::IsOpened`, `wxFile::Eof`, the read cut to what is left, `wxFile::Read`, and when the flag is set a `wxFile::Seek` to base + position. Only the offsets differ: position `+0x48` -> `+0x50`, length `+0x50` -> `+0x58`, flag `+0x34` -> `+0x3C`, base `+0x40` -> `+0x48`; **one 8-byte member was added in front of `+0x34`**. The emulator's "different library calls" were this (it feeds both builds the same block, so each reads another member), and so are the getters that returned other numbers. Nothing changed in what the class does.
- **The plugin system (read in outline: the calls and strings of `TGameControl::InitScripts`, all of `registeractionpart`, the action part lookup in `TGAction::Execute`).**
  - `InitScripts` still runs `controller.lua`. New: it reads the game record's list of plugins (field `0x35F`, `GamePlugins`) and its list of names of custom action parts (`0x359`, `GameCustomActionParts`), and sets the global Lua function **`registerActionPart`** (a C function, `registeractionpart(lua_State *)`).
  - For each plugin (`TTPlugin`: `PluginActive` `0x35C`, `PluginDirectory`, `PluginData`) that is active, the plugin's description is read from a file in the containers (`TComposedFileManager::GetMemoryFile`) as an INI file (`wxFileConfig` made from the buffer) with the entries `Name`, `Author`, `Date`, `Version`, `Description` and `ActionParts`, a `sha1` is looked at, and a Lua file of the plugin is run with `LuaDoFile` (the texts `/plugins`, `/editor.lua` and `/player.lua` are in `InitScripts`; how they are used was not read). The messages are "plugin directory '%s' or files missing" and "plugin info '%s' missing". How the `ActionParts` names are tied to ids and what the `sha1` checks was not read.
  - `registerActionPart(name, function)`: the first argument is a string (the name of the action part), the second must be a function (`lua_type` 6); the function is kept as a reference in the Lua registry (`luaL_ref`) and put in a map by the id of the part; an id that is already there gives "tried to register a claimed action part", a name that is not found or a second argument that is not a function gives "%s id not found or wrong arg type".
  - `TGAction::Execute`: before the switch over the built-in action part types (163 cases, 5 to 167) it looks the type up in the static hash map **`TGAction::actionPartHook`** (id -> Lua function reference); when it is there the function is called (`LuaExecuteFunction(int, args, results)`) and the result must be a boolean (`lua_type`, `lua_toboolean`), else "Action part '%s' must return a boolean".
  So **a plugin can add action parts that are implemented in Lua**; the data stores which plugins a game uses (version 189 of the project format). A merged engine needs this only for games that have plugins; the script API is `registerActionPart`.
- **The new kind 20 of typed values is a list of booleans (read: the size table and the schema).** 0x28 bytes is `sizeof(std::vector<bool>)` of the 64-bit libstdc++. It is used by **one field**, `TTCondition.ConditionConditionsNegate` (id 845, project version 187), next to the new `TTCondition.ConditionConditions` (id 844, a list of links to conditions, version 187). So **a condition can now combine any number of conditions, each negated or not**, where Deponia 1 has two (`ConditionCondition1` / `ConditionCondition2` with `ConditionCondition1Negate` / `...2Negate`; those fields are still there). `TArgument::GetBoolList` / `Add(bool)` / `Set(vector<bool>)` are the script side. The fields added to the project format come with the versions 187 (conditions), 188, 189 (plugins and events), 190 and 192 (blocks); Deponia 1's highest is 186.
- **`TGWaySystem::CheckPosition` is the same function (read in both).** Deponia 1 calls `PointInTriangleTolerant` and `PointInTriangle`; the new build has `PointInTriangleTolerant` inline: the same barycentric test with the same tolerance, -0.2 (`0xBFC999999999999A`, which Deponia 1 has in the free function `PointInTriangleTolerant`; the float comparison counted it as new only because it sits in `T*` code now) and the same cache of the triangle area (the byte at `+6` and the double at `+8` of the triangle) in both builds.
- **`TGCharacter::CheckTurning(int)` became `CheckTurning(int, bool)` and does more (read in outline).** The turn is still decided by the directions of the character's turn animations within 30 degrees (`0x1D`/`0x1E`), but the new build also compares two links (fields `0x1D5` and `0x1F7`), calls `TTAnimation::IsModelAnimation` (the animations made of 3D models of the schema: `AnimationModelFile`, `OutfitModelFiles`, `OutfitModelTurnSpeed`), reads the sprites of the animation (`0xEB`), works with the double `360.0` (`qword_E15B00`) and a character field `0x11D`, and starts the turn with `StartCharacterAnim(TVisObjRef &, TCharacterAnimEnum, bool, int)` (animation kind 6). So **turning has a path for model animations that Deponia 1 does not have**; what the numbers do in it was not read.

## The reconstruction on this game's data (R)

`GAME_PASSW=vBdK3x8pXRGNhg` and `tests/deponia1/realdatatest.exe` run in the game folder: the directory is read and the tables load (`PreLoad`, the same `table 21 not in sync` message as in every game), the interfaces load. With `src/deponia1` the run stops at `lua_dump not supported` (the Shader Toolkit script, as for Deponia 4); with the build of `src/deponia4`,
which replaces `string.dump` by an error, the run goes on to the scripts and fails on Lua 5.3 syntax (above). So the data format is read by the reconstruction as it is; **Lua 5.4 is what stops it.**
