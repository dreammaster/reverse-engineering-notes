# Reverse-engineering manifest

Generated by `tools/classify_functions.py` from an IDA `.asm` export. Every
function in the binary gets bucketed as either a known third-party/vendored
library (link the real thing, don't reimplement) or Visionnaire's own
proprietary code (the actual reverse-engineering workload), then the
proprietary functions are grouped by owning class/namespace.

Regenerate after adding a vendor pattern or getting a new game's `.asm`:

```bash
python tools/classify_functions.py <GameName>_Linux.asm --cppfilt c++filt
```

It's safe to re-run at any time - `status` columns in
`proprietary_classes.tsv` / `proprietary_functions.tsv` are preserved across
re-runs (keyed by owner / raw symbol name) even though everything else is
fully regenerated from the `.asm`.

## Files

- **`vendor_libraries.tsv`** - one row per detected third-party library:
  name, function count, address range (as asm line numbers - see caveat
  below), and a few sample demangled names so a classification can be sanity
  checked at a glance.
- **`proprietary_classes.tsv`** - one row per proprietary class/namespace,
  ordered by first appearance in the `.asm` (i.e. address order). Columns:
  `owner`, `status` (`todo` / `in-progress` / `done`, hand-edited), method
  count, first/last line.
- **`proprietary_functions.tsv`** - one row per proprietary function, for
  marking individual methods done within a large class. Columns: `line`,
  `raw_symbol`, `status`, `owner`, `member`, `demangled`.
- **`unclassified_samples.tsv`** - functions with no `::` owner that matched
  no vendor pattern (i.e. free functions IDA couldn't attribute to a class).
  Mostly genuine proprietary free functions, but worth skimming after a
  re-run in case it reveals a missed vendor library.
- **`source_layout.tsv`** / **`source_layout_summary.tsv`** - generated by
  `tools/extract_source_layout.py` from every `x_assert()` call site's
  embedded `__FILE__`/expression/line (see a game's `NOTES.md` for how this
  works). Confirms which original source file a class actually lived in -
  used to lay out `src/<game>/` to mirror the real project structure rather
  than guessing. Regenerate the same way as the classifier:

  ```bash
  python tools/extract_source_layout.py <GameName>_Linux.asm
  ```

## Deponia 1 survey results (2026-09-24)

20,130 total functions: **11,392 vendor** (56.6%), **8,738 proprietary**
(43.4%) across **517 distinct classes/namespaces**.

Identified vendor libraries, largest first (see `vendor_libraries.tsv` for
the full table): SDL2 (2417 fns, incl. its X11 backend), libstdc++/STL
(1606), tolua++ (1391 - Lua bindings for Box2D), Assimp (1035), HarfBuzz
(973), LuaJIT (757 core + 196 public API), FreeType (484 internal + 203
public API), Box2D (479), libpng (421), libwebp (321), wxWidgets (261, a
small subset - string/file/logging/cmdline utilities only, not the GUI
widgets), Spine 2D skeletal animation runtime (227), libvorbis/ogg (183),
jpgd - Rich Geldreich's public-domain JPEG codec, not real libjpeg (88),
rapidjson (66), libcurl (54), zlib (44), GLEW (37), boost (21), PCRE (15),
rapidxml (13), Scintilla (1 stray reference - the script editor almost
certainly pulls in much more that just didn't get named distinctly).

**Caveat - don't trust a lone symbol name.** Two independent mechanisms in
this build corrupt individual symbol names, so cross-check anything
surprising against how a value is actually *used*, not just what it's
called:

1. **Linker identical-code-folding (ICF)**: unrelated destructors/functions
   that happen to compile to byte-identical code get merged under one
   arbitrary symbol. This is how we found `g_logfile` is really a
   `wxFileName` even though the "assignment" call site resolved to
   `wxString::operator=` (see `src/deponia1/NOTES.md`).
2. **IDA FLIRT misidentification**: 110 otherwise-unrelated functions in
   this binary are labeled `ix86_override_options_after_change` (a real GCC
   *compiler-internal* function that has no business being in a game
   binary). These are almost certainly per-translation-unit static
   initializers (`_GLOBAL__sub_I_*`-style global-constructor stubs) that
   happen to share a short, generic prologue with IDA's signature for that
   GCC function. We hit this exact symbol once already, in `main`, wrapping
   the `std::ios_base::Init` constructor call - so treat any occurrence as
   "some translation unit's global constructor," not literally GCC code.

## Priority / ordering strategy

1. **Never reimplement an identified vendor library from disassembly** -
   identify its version (banner strings, version symbols) and link the real
   upstream source/headers instead. `vendor_libraries.tsv` is the checklist
   of what needs a real dependency set up.
2. **Work the proprietary classes in address-order clusters.** Manually
   verified: a class's methods consistently land contiguously in the
   `.asm` (e.g. all of `TGameController`, `TMasterControl`, `TComposedFile`,
   `TStandardPaths`, `TPictureIO` each occupy one tight, uninterrupted
   range - see git history around the `main()` reconstruction). A handful of
   classes are exceptions where `last_line` is far past `first_line`
   (`TPaintControl`, `TCAnimation` in the table above) - almost certainly
   template instantiations or COMDAT-folded duplicates placed elsewhere by
   the linker, not evidence the clustering heuristic is wrong in general.
3. **Prioritize by what's actually reachable** - start from `main()`'s
   direct dependencies (already stubbed in `src/deponia1`) and expand
   outward through the call graph, rather than working strictly top-to-
   bottom through `proprietary_classes.tsv`, so there's always a compiling,
   runnable executable to check progress against.
4. Update `status` in `proprietary_classes.tsv`/`proprietary_functions.tsv`
   as classes are tackled and commit the manifest alongside the code, so
   progress survives across sessions without re-deriving this survey.
5. **Place a class's files to match `source_layout_summary.tsv` once it has
   a confirmed entry there** (e.g. `TGameController` -> `src/deponia1/
   vsplayer/control/gameController.h`/`.cpp`), matching the recovered
   original directory and file name. Until a class has assert evidence,
   leave it at the top level of `src/<game>/` rather than guessing a
   location - a wrong guess is worse than no placement, since later evidence
   would mean moving it (and its includers) twice.
