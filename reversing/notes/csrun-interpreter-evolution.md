# CSRUN.CPP interpreter: 2002 vs 2011 call structure

While chasing the "single source file" leads generated by
`reversing/scripts/build_leads.py`, three `sub_XXXXXXXX` functions in
`rob_blanc_1.asm` all pointed at `Common/CSRUN.CPP`:

- `sub_42AAAB` (76408→...) → **`ccCreateInstanceEx`** (source line 787).
  High confidence: exact string matches ("null pointer passed",
  "unresolved import '%s'", "internal fixup index error") all fall inside
  its 787–976 body span, and the role (instance loader resolving imports)
  fits.
- `sub_42BF84` (77407–77679) → **`ccCallInstance`** (source line 1879).
  High confidence: verbatim string matches ("too many arguments to
  function", "instance already being executed" — not paraphrased, exact
  text), and the callgraph fits: it's called from two distinct sites
  (`sub_409DC7`, `sub_409E9A`, consistent with a public multi-caller API),
  and it calls `sub_42B394` once internally.
- `sub_42B394` (76408–77360) → **no clean 1:1 match**, see below.

## The interesting part

`sub_42B394` is directly **self-recursive** — it calls itself at two
separate call sites within its own body (disassembly lines 77193 and
77613-ish region). Its string evidence (4x "stack overflow" via the
`PUSH_CALL_STACK` macro, "invalid instruction %d found in code stream",
"specified code offset is not valid", "stack corrupt after function call")
all match text that in the 2011 source lives inside `cc_run_code`
(`Common/CSRUN.CPP:1287`), the main bytecode-interpreter switch loop.

But in the 2011 source, `cc_run_code` is **not** self-recursive. When it
hits a script-to-script call opcode (`SCMD_CALL`/`CALLAS`), it calls a
separate small trampoline, `call_function()` (`CSRUN.CPP:1217`), which just
invokes a native function pointer with up to N args — it does not recurse
back into `cc_run_code`.

That means the disassembly's `sub_42B394` looks like an **earlier,
unsplit** version of this logic: in 2002, the interpreter loop apparently
handled script-to-script calls by recursing directly into itself, and the
2011 source shows this having been refactored into a three-part structure
(`cc_run_code` / `call_function` trampoline / `ccCallInstance` entry point).

**Recommendation:** don't rename `sub_42B394` to `cc_run_code` as if it's a
1:1 match — the control-flow shape genuinely differs. Best treated as "the
2002 predecessor of what became cc_run_code," and worth reading in full
before writing any reconstructed C for it, rather than copying the 2011
`cc_run_code` body verbatim. Left as `new_name: null` / confidence
`medium` in `matches.json` pending a closer read.

## Takeaway for the rest of the project

This is a concrete example of the caution in `CLAUDE.md`: string/role
matches reliably identify *which subsystem/file* a function belongs to,
but across a 9-year gap, function *boundaries* (what got split, merged, or
had a layer inserted) can differ. Treat "same file, same error strings" as
confirmation of subsystem, not proof of an identical implementation.
